# image-transformer
Обновленное тестовое задание на backend разработчика.

## Контекст задачи
Предстоит написать высоконагруженный микросервис для обработки изображений. По HTTP приходит запрос, содержащий картинку в формате PNG, координаты прямоугольной области и тип преобразования. Нужно применить к картинке преобразование, вырезать нужный фрагмент и вернуть результат.

## Требования к окружению и стеку

* **Фреймворк:** .NET 8 (или выше).
* **ОС:** Кроссплатформенное решение. Сервис будет запускаться в Linux-окружении (Ubuntu/Alpine).
* **Ресурсы:** Известно, что контейнер сервиса будет ограничен 8 GB оперативной памяти и 8 ядрами процессора.

## API
Сервис должен принимать запросы на порту `8080` (например, `http://localhost:8080/process/rotate-cw/0,0,20,20`).
Единственный эндпоинт: `POST /process/<transform>/<coords>`

* **Body:** данные изображения в формате PNG (до 100 KB и 1000x1000 пикселей, формат `32bppArgb`). Превышение лимита — `400 Bad Request`.
* **Transform:** `rotate-cw`, `rotate-ccw`, `flip-v`, `flip-h`. Любое другое значение — `400 Bad Request`.
* **Coords:** `x,y,w,h` — координаты области относительно *уже преобразованного* изображения. В случае пустого пересечения области с картинкой — `204 No Content`.

Координаты отсчитываются от левого верхнего угла изображения (левый верхний пиксель имеет координаты 0, 0). Все 4 числа могут быть отрицательными, при этом каждое из них по модулю не превышает 2​31​. Если прямоугольник выходит за границу изображения, он должен быть обрезан по границе изображения. 
Пример корректной строки ​ <coords>​ для изображения размером 100x100: -5,-30,200,50 В этом случае в ответ должна попасть область изображения 0,0,100,20. 
Если пересечение прямоугольника с изображением пустое — нужно вернуть пустой ответ с кодом 204 No Content. 
Если ​ <coords>​ имеет неправильный формат — нужно отправить пустой ответ с кодом 400 Bad Request. 
Если сервис получает запрос другого формата — нужно отправить пустой ответ с кодом 400 Bad Request. 
Внимание! Обрезка изображения выполняется после поворота, т.е. координаты области заданы относительно уже повернутого изображения.

## Требования к стабильности под экстремальной нагрузкой:
1. Если нагрузка превышает возможности сервиса — производительность не должна деградировать. То есть, если сервис способен обработать максимум X rps, при нагрузке X * 2 rps сервис должен всё ещё обрабатывать не меньше X rps. Запросы, до которых очередь дойдет не скоро, можно сразу отклонять с ошибкой. 
2. Производительность сервиса не должна деградировать со временем. Если сервис круглосуточно работает под нагрузкой без перезапусков, никакие ресурсы не должны закончиться и пропускная способность не должна уменьшиться. 
3. Клиенты не должны замечать кратковременные задержки в работе сервиса. Если случилась пауза из-за GC, или ещё по какой-то причине сервис короткое время не обрабатывал запросы, клиенты не должны получить ошибок, если пауза действительно была небольшая.

## Оформление

* Решение должно быть выложено на GitHub.
* В корне репозитория должен лежать `Dockerfile`, с помощью которого можно собрать и запустить ваше приложение одной командой `docker build ...` и `docker run ...`.
* Решение может содержать любые сторонние NuGet-пакеты (например, SkiaSharp или ImageSharp для декодирования PNG), однако основную алгоритмическую часть трансформации пикселей желательно реализовать максимально оптимально.
